# SDD в базе знаний

Здесь лежат продуктовые требования и история их согласованных изменений. Правила подготовки, исполнения и архивирования находятся в [`workflow/`](../../workflow/README.md); этот каталог хранит состояние и результат, а не копию процесса.

## Выбор базы знаний

- Общий контракт и изменение, затрагивающее несколько подпроектов: `KnowledgeBase/SDD/`.
- Контракт и изменение одного подпроекта: `<подпроект>/KnowledgeBase/SDD/` рядом с его локальным `KnowledgeBase/index.md`.
- Один change имеет одного владельца и один план. Для общего изменения поле `Target spec` может указывать локальную спецификацию другого подпроекта. Локальный change не меняет чужую или общую спецификацию без переноса изменения к общему владельцу.

В каждом SDD-корне одинаковая структура: `specs/<область>/spec.md` для действующего контракта, `changes/<имя>/` для открытой дельты с `spec.md`, необязательным `design.md`, `tasks.md` и нужными `inputs/`, `changes/archive/<дата>-<имя>/` для принятой истории. Ссылки в SDD-файлах записываются относительно файла, разрешаются от его фактического расположения и остаются внутри монорепозитория; `Canonical spec`, `Target spec` и `Archive path` записываются от корня монорепозитория.

Основная спецификация и принятые открытые дельты вместе задают актуальные требования; статус реализации хранится отдельно в `tasks.md`. У одного `REQ-*` один владелец. При выборе области сначала читайте общий [индекс](../index.md), затем локальный индекс подпроекта и относящиеся требования по [правилам актуальности](../../workflow/spec-maintenance.md).
