# Актуальность требований

Используйте при предложении, плане, диагностике, правке поведения и ревью. Основная спецификация в `<KB>/SDD/specs/<область>/spec.md` описывает принятый контракт; [выбор KB](../KnowledgeBase/SDD/README.md) зависит от владельца области. Код и результаты проверок показывают фактическое состояние. Совпадение со старым кодом или дата файла сами по себе не доказывают правильность требования.

## Найти действующий контракт

1. По области задачи найдите основную спецификацию. Если её ещё нет, запишите область поиска и предполагаемого владельца; для нового change укажите будущий путь `Canonical spec`, не создавая пустой файл ради формы.
2. Найдите только связанные открытые `KnowledgeBase/SDD/changes/` и локальные `<подпроект>/KnowledgeBase/SDD/changes/`, исключая `archive/`. Ищите по `Canonical spec`, `Target spec`, идентификатору REQ и области, включая общие изменения локального контракта. Принятые `spec.md` дельты учитываются вместе с основной спецификацией; draft — предложение, а не действующее правило. Задачи и реализация дельты могут оставаться незавершёнными.
3. Сверьте нужные утверждения с кодом, настройками и доказательствами той же версии. Зафиксируйте конкретные расхождения в существующем change/bug-файле или ответе для `fast`. Не объявляйте всю спецификацию проверенной по одному разделу.

Для одного требования сохраняйте одного владельца и стабильный `REQ-*`. Если два открытых change несовместимо меняют его, установите явный порядок или запросите решение; время изменения файлов не определяет приоритет. Не переписывайте архивы ради актуализации сегодняшнего поведения.

| Расхождение | Разрешённое действие |
| --- | --- |
| Код нарушает действующее требование | Исправить код, сохранить требование |
| Спецификация неточно описывает уже согласованное поведение | Уточнить затронутый раздел и при необходимости код |
| Неверны оба | Исправить оба в пределах доказанных и согласованных условий |
| Нужно выбрать новое поведение | Спросить продуктовый выбор и провести его через SDD |
| Не хватает основания | Продолжить узкую диагностику или назвать границу вывода |

`fast` может поправить относящуюся основную спецификацию вместе с ограниченным фиксированным поведением. Новая принятая дельта change остаётся в `changes/` своего KB до приёмки; план не переносит её в основной контракт раньше archive. При архивировании сравните исходную базу требования, текущее содержимое и принятый результат. Если текущее равно базе — примените дельту; если уже равно результату — пропустите; иначе разберите конфликт без перезаписи чужих изменений. Сохраняйте прямые относительные ссылки и пересчитывайте их от нового местоположения. Новый основной файл создайте по [шаблону](templates/capability-spec.md), если область раньше не имела спецификации. После переноса выполните [структурную проверку](check_sdd.py) в режиме `--archive-check`; она не разрешает смысловой конфликт вместо человека.
