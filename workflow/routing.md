# Выбор маршрута

Выбирайте действие по смыслу просьбы, а не по наличию команды или активного плана. Явное разрешение пользователя действует на названную область и сохраняется при продолжении. Если просьба сочетает этапы, выполняйте ближайший разрешённый этап и продолжайте дальше, когда последующие этапы тоже разрешены.

| Намерение | Маршрут | Следующее действие |
| --- | --- | --- |
| Небольшая понятная правка, объяснение или ограниченный фикс с известной причиной | `fast` | Выбрать нужные знания и требования, выполнить работу без нового плана |
| Сырая идея, выбор продуктового направления или просьба предварительно проработать фичу | `explore` | [Предварительная проработка](product-shaping.md): brainstorming, discovery либо elaborate по нужной глубине |
| Симптом, у которого причина пока неизвестна | `diagnose` | [Bug Resolver](bug-resolver.md): сначала доказать причину |
| Проверить существующий код, diff, commit или PR | `review` | [Code Review](code-review.md): читать и дать обоснованные замечания |
| Новое поведение, значимое изменение контракта или архитектуры, последовательность зависимых задач | `design` | [SDD](sdd.md): согласовать контракт, затем план и реализацию |

`explore` выбирает глубину по просьбе: brainstorming для вариантов, discovery для рабочего brief, elaborate для развёрнутого brief, готового к `propose`. Все три действия предшествуют `propose`. При запросе на разработку маршрут остаётся `design`: если проблема, ожидаемое поведение и границы уже ясны, сразу переходите к `propose`; если нет — примените только нужную часть [предварительной проработки](product-shaping.md) и продолжите разрешённый SDD-цикл. Полный `elaborate` не становится обязательной стадией каждой фичи. Brief и отдельная пауза между этапами нужны лишь по содержанию задачи, а не ради формы; блокирует продолжение только неразрешённый выбор, меняющий продуктовый контракт. Проверка готового bugfix относится к `review`; неизвестная причина без просьбы проверить решение — к `diagnose`. Из `diagnose` после доказательства причины можно перейти в `fast` или лёгкий bug-план; если меняется продуктовое поведение — в `design`. Ревью не закрывает активный план автоматически. Изменение самого харнеса направляется в [Harness Change](skills/harness-change/SKILL.md).

## Четыре независимых выбора для плановой работы

- **Маршрут** определяет, нужен ли формальный change.
- **Execution profile:** `adaptive` — результат и границы задачи, локальные шаги выбирает исполнитель; `guided` — передача подготовленной задачи с проверенными существенными решениями и конкретными опорами. Профиль выбирают по реальной потребности в передаче, не по имени модели.
- **Execution scope:** `change` — выполнить весь разрешённый план; `task` — остановиться после указанной задачи. Точный номер задачи ограничивает действие этой задачей. Профиль не определяет охват.
- **Evidence profile:** `normal` — самый узкий полезный сигнал; `strict` — более тщательное доказательство для существенного риска. `strict` сам по себе не означает запуск всех проверок.

Явные пожелания пользователя имеют приоритет. Иначе выбирайте разумный режим из запроса и среды: обычно `adaptive`, охват по формулировке задачи, `normal`, а при названном существенном риске — `strict`. Перед созданием `tasks.md` сохраните три последних выбора там. Уточняйте только реально неоднозначный выбор, который меняет выполнение; уже сохранённые значения повторно не спрашивайте. Для `fast` эти поля не нужны.

Название скилла или команда (`brainstorming`, `discovery`, `elaborate`, `propose`, `plan`, `implement`, `archive`) — алиас действия, а не обязательный интерфейс. «Составь план» начинает с недостающего контракта; «реализуй» при уже разрешённом полном цикле включает нужную подготовку, если она требуется для ясного контракта. «Прими и закрой» применяется лишь к актуальному готовому результату. Commit, push, PR и публикация не следуют из архивации.
