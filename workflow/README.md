# Рабочий процесс монорепозитория

Здесь находится общий Harness 2.0 для цифрового тьютора и будущих подпроектов. Он описывает принятие решений и ведение работы; конкретные языки, платформы, сборки и проверки определяются подпроектами, когда они появятся. Источник общих продуктовых знаний — [KnowledgeBase/index.md](../KnowledgeBase/index.md), расположение SDD-артефактов — в [карте SDD](../KnowledgeBase/SDD/README.md).

## Первый проход

1. Понять запрос, уже данное разрешение и границы работы. Выбрать маршрут по [карте](routing.md): `fast`, `explore`, `diagnose`, `review` или `design`. Названия скиллов и команды — необязательные способы вызвать тот же процесс.
2. Найти владельца области, прочитать нужные локальные инструкции и выбрать только относящиеся знания через [индекс](../KnowledgeBase/index.md). [Контекст](context.md) объясняет восстановление состояния между сессиями.
3. Для `fast` выполнить ограниченную работу без артефактов ради формы. Для `explore` прочитать [предварительную проработку](product-shaping.md); для `diagnose` — [Bug Resolver](bug-resolver.md); для `review` — [Code Review](code-review.md); для `design` — [SDD](sdd.md) и документ текущего этапа, добавляя проработку только при недостающей продуктовой ясности. При длинной работе учитывать [Ledger](ledger.md) только в пределах подтверждённой активности host-адаптера.
4. Перед техническим выбором сверить относящиеся действующие требования и реализацию по [правилам спецификаций](spec-maintenance.md). После работы сообщить результат, доказательства, ограничения и ближайший шаг.

Для нового поведения общий путь — предварительная проработка по необходимости → `propose` → `plan` → `implement` → приёмка → `archive`. `brainstorming`, `discovery` и `elaborate` всегда находятся до `propose`; полный elaborate выбирайте по просьбе о глубокой предварительной проработке. Уже разрешённый цикл продолжается без отдельной остановки между этими шагами, если нет открытого решения, меняющего контракт.

## Владельцы состояния

| Где | Что хранится |
| --- | --- |
| `KnowledgeBase/` и `<подпроект>/KnowledgeBase/` | Общие и локальные долговременные понятия, правила и продуктовые SDD; вход через соответствующий индекс |
| `<KB>/discovery/<тема>.md` | Рабочий brief предварительной проработки, если её нужно сохранить между сессиями; не принятый контракт |
| `<KB>/SDD/specs/<область>/spec.md` | Принятый основной контракт владельца области |
| `<KB>/SDD/changes/<изменение>/spec.md` | Источники, согласованные требования и дельта контракта |
| `<KB>/SDD/changes/<изменение>/design.md` | Только существенные технические решения, когда нужны |
| `<KB>/SDD/changes/<изменение>/tasks.md` | Единственный план, режим исполнения, задачи, результаты и приёмка |
| `<KB>/SDD/changes/<изменение>/inputs/` | Нужные снимки недолговечных исходных материалов, без секретов |
| `<KB>/SDD/changes/archive/<дата>-<изменение>/` | Принятое историческое изменение |
| `workflow/bugs/<имя>.md` | Временное состояние нетривиального диагноза или лёгкого bug-плана |
| `workflow/reviews/<имя>.md` | Состояние ревью, только если нужно продолжение между сессиями |

Не создавайте пустые артефакты для `fast`, короткого расследования или короткого ревью. В одном рабочем дереве бывает один план `active`; готовых `awaiting_acceptance` может быть несколько. Цель выбирается по явному запросу и содержимому артефактов, не по времени изменения файла.

`<KB>` здесь означает `KnowledgeBase` для общей области или `<подпроект>/KnowledgeBase` для одного подпроекта. Изменение нескольких подпроектов хранится в общем SDD-корне. После составления плана и перед архивированием выполните [структурную проверку](check_sdd.py) выбранного каталога; она проверяет форму и перенос, а смысловую сверку выполняет агент.

## Процессы

- [Маршрутизация](routing.md) — намерение, профиль, охват и уровень доказательств.
- [Продолжение и алиасы](commands.md) — выбор текущего change, точной задачи и поведение при паузе или приёмке.
- [Контекст и знания](context.md) — выбор фактов, чтение, возобновление работы.
- [Предварительная проработка](product-shaping.md) — brainstorming, discovery и elaborate до технического плана.
- [SDD](sdd.md), [планирование](sdd-planning.md), [сверка плана](plan-review.md), [исполнение и закрытие](sdd-execution.md) — изменение с контрактом и планом.
- [Актуальность спецификаций](spec-maintenance.md) — текущие требования, дельты и перенос при архивировании.
- [Bug Resolver](bug-resolver.md) — причинная диагностика симптома.
- [Code Review](code-review.md) — проверка готового решения без исполнения.
- [Ledger](ledger.md) — пассивные наблюдения, проектные hooks Codex и Claude Code, границы активации.
- [Обращение с меняющимися медиаисточниками](source-materials.md) — версия макета, голоса, аватара, анимации и материала, когда результат от них зависит.
- [Сценарии оценки харнеса](evals/README.md) — отдельная проверка применения процесса на характерных задачах.
- [Узкая защита данных](safety-hooks.md) — pre-tool защита от типичных разрушительных действий и записи файлов секретов.

Канонические скиллы хранятся в `workflow/skills/`. Каталоги `.agents/skills/` и `.claude/skills/` содержат относительные ссылки на них для Codex и Claude Code. Новые скиллы публикуются по [Harness Change](skills/harness-change/SKILL.md). Скиллы служат короткими входами в общие документы, не копируют процесс.
